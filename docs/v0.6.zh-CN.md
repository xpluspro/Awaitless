# Awaitless v0.6：Adaptive Run

状态：Implemented

依赖基线：v0.5.0

发布日期：2026-08-18

## 一句话目标

> Agent 只选择要执行的非交互命令；Awaitless 自动决定结果应当 inline 返回，还是作为
> durable Job 脱离当前调用继续运行。

v0.6 解决的不是新的 Backend 能力，而是 Agent 的 routing friction。只要同步 Shell 或 SSH
仍然能工作，模型就会偏向立即获得 stdout 和 exit code，并合理化继续阻塞。要求模型先判断
任务时长，再在 `submit`、`status`、`logs`、`wait` 之间组织生命周期，会让 Awaitless 的
采用率依赖提示词纪律。

本版本把首选抽象从“提交一个长任务”改成“运行一个命令”：

```text
run(command)
    │
    ├── durable record + supervised launch from time zero
    │
    ├── finishes inside inline window → bounded result inline
    │
    ├── still active at deadline      → durable Job handle + bounded logs
    │
    └── target has a default queue    → queue immediately, return handle
```

## 1. 外部接口

### MCP

首选 Tool：

```text
run(command, backend?, host?, cwd?, env?, timeout_seconds?,
    stall_timeout_seconds?, inline_timeout_seconds?, name?, artifacts?,
    slurm_options?, client_request_id?, queue?)
```

快速完成时：

```json
{
  "job_id": "job_...",
  "state": "succeeded",
  "exit_code": 0,
  "stdout_tail": "...",
  "delivery": "inline",
  "detached": false,
  "inline_timeout_seconds": 30
}
```

超过 inline deadline 时：

```json
{
  "job_id": "job_...",
  "state": "running",
  "stdout_tail": "...",
  "delivery": "detached",
  "detached": true,
  "detach_reason": "inline_timeout",
  "inline_timeout_seconds": 30
}
```

`detached` 是正常成功的路由结果，不是 workload timeout。任务继续运行，并可通过
`wait_for_job`、`wait_for_completions`、`get_job_status` 或 MCP Tasks 恢复。
`detach_reason` 为 `inline_timeout` 或 `queued`，避免客户端根据活动状态猜测路由原因。

### CLI

```bash
awaitless run --json -- ninja -C build
awaitless run --inline-timeout 10s --json -- ./benchmark
```

CLI 与 MCP 使用相同结果契约。inline 完成时 CLI 返回 workload 对应的 Awaitless exit code；
detach 成功时返回 0。`--timeout` 仍然限制 workload runtime，`--inline-timeout` 只限制当前
调用保持 inline 的时间。

## 2. 从启动时就是 durable

v0.6 不启动一个临时同步进程，再在 deadline 后迁移。每次 `run` 都先复用现有 `submit`
事务、稳定 Job ID、幂等边界和 Backend supervisor。inline window 只是结果交付策略：

```text
durable submit → wait up to inline deadline → inline result or detach waiter
```

因此不会出现升级时重复执行、丢失 PID、日志切换或取消语义变化。客户端断开也只影响当前
waiter，不影响 workload。

## 3. Operator-owned queue routing

Agent 可以显式传 `queue`，但首选路径允许 Operator 在配置中绑定默认 queue：

```toml
[defaults]
adaptive_inline_timeout_seconds = 30
queue = "gpu0"

[hosts.ascend]
hostname = "ascend.example.com"
queue = "910b3"
```

`run` 在未显式指定 queue 时按 selected host、全局 default 的顺序解析。Slurm 不使用
Awaitless queue，继续由 Slurm 调度资源。低层 `submit` 不隐式采用 default queue，以避免
改变已有自动化语义。

进入 named queue 的 adaptive run 会立即 detach。`queued` 是有效执行状态；Agent 不需要先
调用设备探测、维护锁文件或选择轮询间隔。

## 4. 兼容性

以下接口保持不变：

- `submit_job` / `awaitless submit`：明确的 fire-and-recover 低层入口；
- `run_job`：MCP Tasks 与 legacy blocking 兼容入口；
- `wait_for_job` / `awaitless wait`：单 Job terminal result；
- `wait_for_completions` / `awaitless completions`：多 Job durable cursor；
- status、logs、cancel、list、queue 与 inspect。

v0.6 没有实现宿主级 push 或自动执行下一步 reasoning。Awaitless 负责保留 continuation
result；Agent 宿主是否在 completion 后主动唤醒 session，仍取决于未来 adapter。

## 5. 配置

新增：

```toml
[defaults]
adaptive_inline_timeout_seconds = 30
queue = "optional-default-queue"
```

每个 host 也可以配置 `queue`。inline timeout 必须非负；0 表示提交后立即返回 durable
handle。显式 queue 仍必须预先通过 `awaitless queue create` 创建，且只适用于 Local/SSH。

## 6. 验收标准

- 快速命令返回 terminal state、exit code、有界日志和 `delivery=inline`；
- 长命令在 deadline 后返回 `delivery=detached`，随后可由新客户端取得同一 Job 的结果；
- detach 不取消、不重启、不重复提交 workload；
- configured default queue 在 MCP 与 CLI 的 adaptive `run` 中生效；
- queued adaptive run 立即返回 handle，并在获得容量后执行；
- `submit_job`、`run_job`、MCP Tasks 和 completion feed 保持兼容；
- 文档与 Skill 把 `run` 作为非交互工程命令的默认 Awaitless 入口。
