# Awaitless v0.5：Durable Completion Feed

状态：Implemented

依赖基线：v0.4.0

发布日期：2026-08-12

## 一句话目标

> Agent 提交一组工作后，可以从一个持久、可重放的入口消费已经完成的结果，而不必逐个
> Job polling，也不必保持原始 session 存活。

v0.5 补齐 Awaitless 的第三条产品主线：**completion / continuation**。

它不让 Awaitless 接管 Agent 推理，也不承诺唤醒一个已经关闭的 Agent 进程。它提供的是
更底层、可验证的事实：任务完成后产生一个持久 completion；当前客户端可以阻塞等待，
重连后的客户端可以用 cursor 重放，Agent adapter 可以把它映射成自己的 continuation。

## 1. 为什么是这个版本

v0.4 已经闭环：

- Local、SSH 和 Slurm 的持久 Job；
- 稳定 Job ID、状态、取消、有限日志和 JSON Artifact；
- 基于 `client_request_id` 的幂等提交；
- Local / SSH 持久命名 FIFO 队列；
- MCP Tasks handle 与断线恢复。

但当前结果消费仍以单 Job 为中心：

```text
submit A → retain A → wait/get A
submit B → retain B → wait/get B
submit C → retain C → wait/get C
```

如果 Agent 一次提交多个 benchmark、build 或 experiment，它必须逐个重新访问 Task handle，
或自行维护“哪些任务已经完成”的集合。Job 的终止状态已经持久化，但还没有成为一个稳定的
多 Job 结果入口。

v0.5 把它改成：

```text
submit A / B / C
→ continue useful reasoning
→ read completions for A / B / C after cursor
→ consume every currently available bounded result
```

这一步比 priority、抢占、GPU discovery 或更多 Backend 更接近 Awaitless 的核心品类。

## 2. 产品决策

### 2.1 Completion 是持久事实

每个 Job 第一次进入终止状态时，必须产生且只产生一个 completion：

```text
succeeded | failed | cancelled | timed_out | lost
```

completion 独立于读取它的 CLI 或 MCP session。关闭 waiter、重启 stdio server 或重新打开
Agent session 后，它仍然存在。

### 2.2 Cursor 是消费边界

completion feed 使用单调 cursor：

- 相同 cursor 的重试可以重放相同 completion；
- 客户端只在成功消费结果后保存 `next_cursor`；
- cursor 之后没有结果时，调用可以阻塞到新 completion 或调用级 timeout；
- timeout 只结束本次等待，不取消任何 Job。

v0.5 提供 **at-least-once read**，不承诺 exactly-once consumption。客户端使用稳定
`completion_id` 去重。服务端不在 v0.5 引入 consumer ownership 或自动 ack，以免过早建立
多租户消息队列语义。

### 2.3 Agent-facing event-driven，不等于所有 Backend 都无轮询

Local runner 可以直接写入持久状态；SSH 与 Slurm 的状态仍可能需要 Awaitless 在一个调用
内部低成本刷新。产品保证的是 Agent 不需要为每个 Backend 编写 polling reasoning loop，
而不是声称底层基础设施从此不存在状态查询。

### 2.4 Continuation 只交付结果

Awaitless 不在 Job 完成后自动运行下一条 Shell 命令、修改代码或向 Agent 注入 prompt。
completion 包含“什么完成了”和“结果是什么”；下一步仍由 Agent 决策。

## 3. 接口契约

以下接口已在 v0.5 实现；v0.4 及更早版本不支持这些命令。

### 3.1 CLI

```bash
awaitless completions \
  job_019F_A job_019F_B job_019F_C \
  --after cmp_0000000000000042 \
  --timeout 10m \
  --limit 50 \
  --json
```

行为：

1. 先刷新所选 Job 中仍处于活动状态的 Job；
2. 如果 cursor 后已有 completion，立即返回当前可用的一批；
3. 如果没有，则在一次调用内部等待，直到至少一个 Job 完成或等待超时；
4. 一次返回 cursor 后目前可用的多个 completion，最多 `limit` 个；
5. 不读取未声明的完整日志，不自动取消任何 Job。

v0.5 要求至少传入一个 Job ID。全局订阅、按任意标签订阅和服务端持久 consumer 暂不加入，
避免把第一个版本扩张成通用消息系统。

响应示例：

```json
{
  "completions": [
    {
      "completion_id": "cmp_0000000000000043",
      "job_id": "job_019F_B",
      "state": "succeeded",
      "finished_at": "2026-08-12T10:20:31Z",
      "observed_at": "2026-08-12T10:20:32Z",
      "result": {
        "job_id": "job_019F_B",
        "state": "succeeded",
        "finished_at": "2026-08-12T10:20:31Z",
        "exit_code": 0,
        "duration_seconds": 81.4,
        "stdout_tail": "...",
        "stderr_tail": "",
        "truncated": false,
        "artifacts": [],
        "parsed_results": {"latency_us": 18.7}
      }
    }
  ],
  "next_cursor": "cmp_0000000000000043",
  "active_job_ids": ["job_019F_A", "job_019F_C"],
  "unreachable_job_ids": [],
  "has_more": false,
  "wait_timed_out": false
}
```

`finished_at` 表示 Backend 能确认的实际结束时间；`observed_at` 表示 completion 进入本地
持久 feed 的时间。远端 Job 在断线期间结束时，两者可能不同。Feed 顺序以 completion cursor
为准，不伪装成所有机器之间的严格全局完成时间顺序。

第一批读取可以省略 `--after`，语义为“返回所选 Job 已经存在的全部 completion”；读取后
使用返回的 `next_cursor`。同一组消费流程不得在中途改变 Job filter 后继续复用 cursor。

### 3.2 MCP

增加普通 MCP Tool：

```text
wait_for_completions
```

输入示例：

```json
{
  "job_ids": ["job_019F_A", "job_019F_B", "job_019F_C"],
  "after_cursor": "cmp_0000000000000042",
  "timeout_seconds": 600,
  "limit": 50
}
```

输出与 CLI JSON 共用同一 Schema。`timeout_seconds: 0` 是非阻塞读取；正数是有界长等待；
省略时允许像现有 `wait_for_job` 一样持续等待。

机器可读契约位于
[`docs/schemas/completion-feed.schema.json`](schemas/completion-feed.schema.json)。

一次最多选择 500 个 Job，`limit` 范围为 1 至 500。`has_more` 表示 cursor 后仍有未返回
的 completion；`unreachable_job_ids` 表示终止结果暂时无法从 SSH/Slurm 取回。Awaitless
不会越过不可交付的 completion，客户端应保留原 cursor 重试。

这个 Tool 对支持和不支持 MCP Tasks 的客户端都可用。v0.5 不发明新的 MCP push capability，
也不改变现有 `run_job`、`tasks/get` 和 `wait_for_job` 的兼容行为。

### 3.3 现有接口兼容性

- `awaitless wait <job-id>` 继续是单 Job 最短路径；
- `tasks/get` 继续按当前 MCP Tasks 兼容层工作；
- `list_jobs` 继续用于观察，不替代 completion cursor；
- `submit` 的 JSON 契约保持兼容；
- completion 内嵌结果继续服从现有 `max_return_bytes` 与日志尾部限制。

## 4. 数据与一致性设计

### 4.1 复用终止状态事件

优先把现有 SQLite `state_events` 的终止事件作为 completion source，而不是复制整份结果：

- 暴露事件的单调 ID，并编码为不透明 `completion_id`；
- 为终止状态查询增加合适索引；
- Job 状态更新和 terminal event 插入保持同一事务；
- 每个 Job 最多一个 terminal event；
- 读取 completion 时再从 Job、有限日志和声明 Artifact 组装 result。

这样不会把日志或 Artifact 内容重复存入 SQLite，也让现有 `inspect` 状态历史继续是事实来源。

### 4.2 v0.4 数据库升级

迁移必须原地完成并保留所有历史 Job：

- 已有 terminal event 的 Job 直接进入 feed；
- 极端情况下，terminal Job 缺少 terminal event 时按 `finished_at`、`job_id` 稳定回填；
- 回填事件的 `finished_at` 保留历史值，`observed_at` 使用迁移观察时间；
- 重复运行迁移不得生成第二个 completion；
- v0.4 的 queue schema、Job ID 和 MCP Task ID 不变。

### 4.3 读取与重试语义

- 同一 `after_cursor + job_ids + limit` 在 feed 未变化时返回相同的 completion ID 与顺序；
- `next_cursor` 只越过已经返回的 completion；
- 未知 Job ID 整体报错，避免静默漏结果；
- 已过期的 MCP Task handle 不删除底层 Awaitless completion；
- cancellation 产生正常 completion，不能作为协议错误丢弃；
- `failed`、`timed_out` 和 `lost` 都必须携带可用的有界诊断结果。

### 4.4 Backend reconciliation

- Local：runner 写入 terminal transition 后，新进程可直接读取；
- SSH：只刷新调用中选中的活动 Job，临时连接失败保持活动状态并继续有界重试；
- Slurm：复用 `squeue` / `sacct` 刷新和现有状态映射，不建立第二个 Scheduler；
- queued Local / SSH Job：在真正启动前取消也产生 `cancelled` completion；
- 不因 completion waiter 断开而改变 Backend Job。

## 5. 发布范围

### P0：v0.5 已交付

- 一 Job 一个持久 terminal completion；
- 单调、可重放的 completion cursor；
- 多 Job `awaitless completions` CLI；
- `wait_for_completions` MCP Tool；
- 非阻塞读取与有界长等待；
- 与 `wait_for_job` 相同的有限日志和 Artifact 结果契约；
- Local、SSH、Slurm 和 queued cancellation 的一致行为；
- v0.4 SQLite 原地升级与幂等回填；
- 并发读、重连、分页、timeout 和错误路径测试；
- 一个“两次提交、关闭客户端、新客户端消费两个结果”的演示；
- README、Reference、MCP 文档和 Agent Skill 更新。

### P1：只有 P0 稳定后才考虑

- 按 queue 选择 Job；
- 按精确 `name` 选择 Job；
- 在 `list_jobs` / `inspect` 中显示 `completion_id`；
- 把多 Job continuation case 扩展为完整 Agent benchmark 矩阵；
- completion 等待的可配置 Backend 刷新节流。

P1 不得阻塞 v0.5 发布。

## 6. 明确非目标

v0.5 不加入：

- 唤醒已经退出的 Codex、Claude Code 或其他 Agent 进程；
- Webhook、任意 Shell callback、邮件或消息通知；
- 服务端 consumer group、租约、ack 或 exactly-once delivery；
- Workflow DAG、任务依赖或成功后自动提交下一条命令；
- priority、抢占、queue reorder、GPU discovery 或动态资源配额；
- 常驻 daemon、HTTP control plane 或托管服务；
- 日志流式推送；
- Artifact 内容快照或对象存储；
- 新 Backend。

这些能力有的未来有价值，但不能和 durable completion primitive 在同一版本同时设计。

## 7. 实施里程碑

### Milestone 0：冻结契约

产出：

- CLI 参数、JSON Schema 和 MCP 输入输出；
- cursor、排序、重放、timeout 和 filter 语义；
- terminal state 与错误映射；
- v0.4 迁移样例。

退出条件：仅凭契约即可写黑盒测试，且不存在“读取是否自动 ack”“timeout 是否取消 Job”
一类歧义。

### Milestone 1：Store 与 Service

主要文件：

- `src/awaitless/db.py`：completion 查询、索引、唯一性与迁移；
- `src/awaitless/service.py`：多 Job reconcile、cursor read、阻塞等待和 result 组装；
- `src/awaitless/constants.py`：复用 terminal state 定义；
- `tests/test_db.py`：并发、回填、重放和分页。

退出条件：Local Job 在原客户端退出后，新 Service 实例能用 cursor 读到唯一 completion。

### Milestone 2：CLI 与 MCP

主要文件：

- `src/awaitless/cli.py`：`completions` 命令与退出行为；
- `src/awaitless/mcp_server.py`：`wait_for_completions` Tool；
- `tests/test_cli.py`：参数、JSON、timeout、断线与多 Job；
- `tests/test_mcp.py`：新旧客户端、结果预算和 Task 兼容性。

退出条件：同一组 Job 通过 CLI 和 MCP 得到等价 Schema；中断任一 waiter 后 Job 与 feed 都
保持可恢复。

### Milestone 3：Backend 验收

主要验证：

- Local 并发完成与 queued cancellation；
- 两个独立 SSH 客户端提交和消费；
- SSH 瞬时不可用不产生虚假 `lost` completion；
- 真实 Slurm `PENDING → RUNNING → terminal → completion`；
- 多 Job 完成顺序与 `finished_at` / `observed_at` 区分。

没有真实 Slurm 环境时可以条件跳过发布机器验收，但必须保留 Fake SSH / Slurm 自动化测试，
并在发布记录中明确说明跳过条件。

### Milestone 4：Agent 证据与发布

产出：

- 更新内置 demo，证明旧客户端消失后新客户端消费多个 completion；
- 更新 `skills/awaitless/SKILL.md`，指导 Agent 在并行工作时使用 completion feed；
- 在受控 Agent case 中比较逐 Job polling 与 completion feed；
- 更新 README、Reference、MCP Tasks 文档、Changelog 与发布元数据；
- 从已安装 wheel 运行 smoke test，而不是只在源码树测试。

退出条件：文档中的每个核心 continuation 声明都有自动化测试或机器可读的真实验收记录。

## 8. 验收标准

| 场景 | 必须观察到的结果 |
|---|---|
| Local 断线恢复 | 提交两个 Job 后关闭原客户端；新客户端收到两个唯一 completion |
| 已完成再订阅 | Job 在调用 `completions` 前已结束，首次读取仍立即返回 |
| 等待中断 | 终止 completion waiter 不取消任何 Job；再次调用可恢复 |
| 多 Job 乱序完成 | 返回顺序按 cursor，且每项保留正确 `finished_at` 与 Job 结果 |
| Cursor 重放 | 使用旧 cursor 重试可再次得到相同事件；使用 `next_cursor` 不重复 |
| 分页 | 超过 `limit` 时无丢失、无跳跃，连续 cursor 最终覆盖全部结果 |
| 调用级 timeout | 返回 `wait_timed_out: true` 和活动 Job；Job 继续运行 |
| queued cancellation | 命令从未启动，同时产生一个 `cancelled` completion |
| 失败与超时 | completion 含退出码、状态和有界诊断，不伪装成 MCP 协议失败 |
| 大日志 | 每个 completion result 的日志遵守现有预算并正确标记 `truncated`；批次数量受 `limit` 限制 |
| Artifact | 单个小 JSON Artifact 继续映射为 `parsed_results` |
| v0.4 升级 | 历史 Job、queue 和 Task ID 保留；迁移重复运行不重复 completion |
| SSH 重连 | 远端完成后新本地 session 能发现结果；临时断线不制造终止事件 |
| Slurm | 调度器终态只映射出一个 completion，取消路径同样成立 |

## 9. 质量与发布门槛

### 正确性门槛

- 每个 terminal Job 恰好一个 completion；
- 自动化并发测试至少覆盖两个独立 SQLite connection；
- 所有 Backend 共用同一外部 completion Schema；
- 现有 v0.4 CLI、MCP Tasks、queue 和幂等提交测试全部保持通过；
- 安装包 smoke test 能从两个独立进程完成 submit → disconnect → consume。

### Agent 体验门槛

受控案例至少包含三个不同耗时的 Job。完成管理阶段不得出现 Agent 驱动的周期性 `status`、
`sleep`、`tail` 或 `tasks/get` 循环。Agent 可以在一个 completion 调用内等待，也可以先继续
推理、之后读取已经可用的批次。

指标重点是：

- completion 的漏失率和重复可识别率；
- session 重建后的恢复成功率；
- Agent-visible 任务管理调用；
- 进入上下文的日志字节数；
- 状态、退出码和 Artifact 正确率。

不预设“必然比所有定制 wrapper 更省 token”的结论。

## 10. 风险与缓解

### 10.1 把 completion feed 误解成 Agent push

缓解：文档始终使用“durably available / 可持久消费”，不承诺在没有宿主集成时主动唤醒
一个已退出的进程。未来 Agent adapter 可以在 feed 之上增加 wakeup。

### 10.2 远端完成时间与发现时间不同

缓解：同时返回 `finished_at` 和 `observed_at`，cursor 只表示稳定消费顺序，不表示跨机器
绝对时间顺序。

### 10.3 Cursor 使用错误导致重复处理

缓解：提供稳定 `completion_id`、确定性重放和清晰示例；v0.5 接受可去重的重复，不提供
可能造成结果丢失的隐式自动 ack。

### 10.4 扫描所有历史活动 Job 造成成本增长

缓解：v0.5 要求显式 Job ID 集合，只刷新其中的活动 Job；全局订阅留到有索引和保留策略后。

### 10.5 结果文件在 Job 完成后被外部修改

缓解：v0.5 延续现有 Artifact 读取语义，不声称内容不可变；如果需要不可变 Artifact，后续
版本单独设计快照、hash 与存储保留策略。

## 11. 发布后再评估

只有 durable completion primitive 经真实 Agent 工作负载验证后，才评估：

1. Agent 宿主的原生 wakeup / notification adapter；
2. 持久 named consumer 与显式 ack；
3. 按 queue、标签或 workflow key 的订阅；
4. completion 保留与垃圾回收策略；
5. 声明式 Job dependency；
6. priority 或更丰富的资源策略。

下一版本是否继续做 continuation adapter，应该由 v0.5 的恢复正确性、实际 Agent 调用轨迹
和用户工作负载决定，而不是预先把 Awaitless 扩张为 Workflow Engine。
