# Awaitless v0.7：Immutable Completion Snapshots

状态：Released

依赖基线：v0.6.0

发布日期：2026-08-19

本版本同时交付结构化 wait 超时、completion drain、终态取消语义、时间单调化、
重定向日志捕获、环境快照、阶段心跳、细分失败原因及显式设备/资源声明。资源队列负责
固定并发和冲突可见性；GPU topology 与多资源物理调度仍委托 Slurm 等调度器。

CLI 结果交付也补充了三个互不混淆的状态字段：`job_state` 表示任务本身，`wait_state`
表示当前等待器，`delivery_state` 表示本次响应是否已经交付终态结果。detached 响应还会
附带可复制的 `next_command`；可用 `awaitless wait --last --json` 恢复最近一次 detached
任务，并用 `awaitless logs <job-id> --grep 'PASS|FAIL|median|CV'` 筛选 benchmark 关键日志。

## 一句话目标

> Awaitless 第一次成功收集终止结果后，后续任何 session 都能得到完全相同的有界结果，
> 不再依赖原日志、Artifact 或远端主机仍然可用。

v0.5 让 completion 的身份、顺序和 cursor 持久化。v0.7 要让 completion 携带的
Agent-facing result 也成为不可变、可校验、可离线重放的持久事实。

## 1. 为什么下一版先做 Snapshot

v0.5 的 durable completion feed 已经解决：

- 每个 terminal Job 只有一个 completion；
- Agent 可以跨 session 按 cursor 重放；
- waiter 断开或超时不会取消 Job；
- 多个 Job 的结果可以从同一个入口消费；
- SSH / Slurm 暂时不可达时不会跳过 completion。

但 v0.5 的 terminal event 只持久化了“Job 已结束”这一事实。返回结果仍在读取时由当前
Job 状态、日志文件和声明的 Artifact 动态组装：

```text
durable completion event
        │
        ├── read mutable stdout/stderr
        ├── read mutable Artifact
        └── contact SSH / Slurm target when remote
                 │
                 ▼
             result payload
```

因此存在四个基础语义缺口：

1. 相同 `completion_id` 在不同时间可能返回不同的日志尾部或 JSON Artifact；
2. 远端结果成功读取一次后，下一次重放仍可能因为 SSH / Slurm 不可达而失败；
3. 本地工作目录被清理后，completion 身份仍在，但有界结果可能不再完整；
4. 客户端无法校验重放结果是否和第一次消费时一致。

这些问题比新增 workset、named consumer、Webhook 或 priority 更接近 Awaitless 的核心承诺：

> **Execution results must survive the session that produced them.**

v0.7 先把结果持久性做实，再在稳定 snapshot 之上扩展更高层 continuation 能力。

## 2. 产品决策

### 2.1 Snapshot 是 Agent-facing result 的不可变副本

当 Awaitless 第一次成功收集一个 terminal Job 的有界结果时，创建唯一 snapshot。内容包括：

- Job ID、terminal state、exit code 与错误摘要；
- `created_at`、`started_at`、`finished_at` 和 duration；
- 按当前配置截断后的 stdout / stderr tail；
- `truncated` 标记与日志字节统计；
- 声明 Artifact 的稳定元数据；
- 当前结果契约允许内嵌的小型 JSON Artifact 与 `parsed_results`。

snapshot 创建后不可更新。后续 `wait`、completion replay 和 MCP result 直接读取 snapshot，
不重新访问 Backend 或原始文件。

### 2.2 Snapshot 不等于完整 Artifact 对象存储

v0.7 只冻结已经会进入 Agent 上下文的有界结果，不复制任意大小的模型权重、构建产物、
数据集或完整日志。

- 小型 JSON Artifact：冻结内容与元数据；
- 大型或非 JSON Artifact：冻结路径、存在性、大小和修改时间等元数据；
- 完整日志：继续保存在现有日志位置，snapshot 只保存有界 tail；
- 未内嵌的大文件内容：不承诺在原基础设施删除后仍可下载。

这样可以保证 Agent 决策输入稳定，又不会把 Awaitless 变成对象存储系统。

### 2.3 第一次捕获仍需要 Backend 可达

Local Job 的结果通常可以直接捕获。SSH / Slurm Job 在 snapshot 尚未创建时，仍需要目标主机
可达才能读取日志与 Artifact。

```text
terminal event
→ first successful result collection
→ immutable local snapshot
→ all later replay is offline
```

如果第一次捕获失败：

- completion cursor 不前进；
- Job 出现在 `unreachable_job_ids`；
- 调用可以在 timeout 内重试；
- 下一 session 使用同一 cursor 继续；
- 不生成空 snapshot，也不把暂时失败固化为永久结果。

### 2.4 Digest 用于一致性校验，不用于身份寻址

snapshot 使用 canonical JSON 编码，并计算 SHA-256：

```json
{
  "schema_version": 1,
  "captured_at": "2026-08-13T08:30:00Z",
  "sha256": "...",
  "size_bytes": 4271
}
```

`completion_id` 继续是消费顺序与去重身份；digest 只证明 result payload 未发生变化。v0.7
不把 Job ID、completion ID 或 Artifact 路径改成内容寻址标识。

### 2.5 无隐式删除

v0.7 不自动清理 snapshot。自动 retention 在没有明确 operator policy 时会破坏持久重放承诺。
本版本只记录 snapshot 数量和字节数，为后续显式 retention / GC 设计提供数据。

## 3. 为什么暂不选择其他方向

| 候选方向 | 当前价值 | 暂缓原因 |
|---|---|---|
| Durable workset / workflow key | 减少 Agent 保存 Job ID 集合的负担 | 会把 mutable result 问题带进更高层对象 |
| Named consumer + ack | 服务端保存 cursor，适合长期 continuation | ack 必须建立在可稳定重放的 result 上 |
| Agent wakeup / notification adapter | 更接近真正的宿主级 continuation | 宿主相关，且不能替代底层结果持久性 |
| Completion retention / GC | 控制长期磁盘占用 | 需要先获得真实 snapshot 体积和访问数据 |
| Priority / GPU discovery | 改善部分资源工作流 | 扩张 scheduler 语义，不是当前正确性瓶颈 |
| DAG / 自动下一步 | 可以表达 workflow | 违反“Reasoning belongs to the agent”边界 |

v0.8 是否进入 workset 与 named consumer，由 v0.7 的 snapshot 大小、重放频率和真实 Agent
调用轨迹决定。

## 4. 外部接口契约

### 4.1 现有命令保持主路径

v0.7 不新增另一套结果读取命令：

```bash
awaitless wait <job-id> --json

awaitless completions job_A job_B job_C \
  --after cmp_0000000000000042 \
  --json
```

第一次成功读取 terminal result 时可能创建 snapshot；之后所有读取都使用 snapshot。

### 4.2 Completion 响应增加 snapshot 元数据

每个 completion 增加向后兼容的 `snapshot` 字段：

```json
{
  "completion_id": "cmp_0000000000000043",
  "job_id": "job_019F_B",
  "state": "succeeded",
  "finished_at": "2026-08-13T08:29:59Z",
  "observed_at": "2026-08-13T08:30:00Z",
  "snapshot": {
    "schema_version": 1,
    "captured_at": "2026-08-13T08:30:00Z",
    "sha256": "83b4...",
    "size_bytes": 4271
  },
  "result": {
    "job_id": "job_019F_B",
    "state": "succeeded",
    "exit_code": 0,
    "stdout_tail": "...",
    "stderr_tail": "",
    "truncated": false,
    "artifacts": []
  }
}
```

同一 `completion_id` 的 `snapshot.sha256` 和 `result` 必须永远一致。

### 4.3 单 Job wait 使用同一 snapshot

`awaitless wait` 与 `wait_for_job` 不维护独立缓存。它们和 completion feed 共用同一份
snapshot：

- 单 Job terminal result 增加顶层 `snapshot`，字段与 completion item 的 `snapshot` 相同；
- digest 输入是 snapshot metadata 之外的 terminal result payload；
- 先 `wait`、后 `completions`：返回相同 result 与 digest；
- 先 `completions`、后 `wait`：同样返回 snapshot；
- 多个客户端并发首次读取：最终只有一份 durable snapshot。

`status` 继续表达当前持久状态，不附带完整 result。`logs` 继续是显式读取当前日志的观察接口，
可能与历史 snapshot tail 不同；文档必须明确这一区别。

### 4.4 Inspect 暴露 snapshot 状态

`awaitless inspect <job-id> --json` 增加：

```json
{
  "result_snapshot": {
    "state": "captured",
    "captured_at": "...",
    "sha256": "...",
    "size_bytes": 4271
  }
}
```

尚未捕获时返回 `state: "pending"`。Inspect 不主动触发远端读取。

### 4.5 MCP 保持兼容

以下 Tool 自动获得相同 snapshot 语义：

- `wait_for_job`；
- `wait_for_completions`；
- `run_job` 的 blocking fallback；
- MCP Tasks 的 terminal result retrieval。

v0.7 不增加自定义 MCP push capability，也不要求客户端支持 MCP Tasks。

## 5. 数据与一致性设计

### 5.1 Snapshot 表

建议新增：

```sql
CREATE TABLE completion_snapshots (
    completion_event_id INTEGER PRIMARY KEY,
    job_id TEXT NOT NULL UNIQUE,
    state TEXT NOT NULL,
    schema_version INTEGER NOT NULL,
    capture_state TEXT NOT NULL,
    claim_token TEXT,
    claim_expires_at TEXT,
    captured_at TEXT,
    result_json TEXT,
    result_sha256 TEXT,
    size_bytes INTEGER,
    FOREIGN KEY(completion_event_id) REFERENCES state_events(id),
    FOREIGN KEY(job_id) REFERENCES jobs(job_id)
);
```

`capture_state` 只有：

```text
capturing | captured
```

不存在记录表示尚未开始捕获。不得创建 `failed` snapshot；暂时失败仍应可重试。

### 5.2 两阶段捕获，网络 I/O 不进入 SQLite 事务

首次读取分为：

1. 在短 SQLite 事务内声明 capture lease；
2. 在事务外读取 Local / SSH / Slurm 的有界结果；
3. canonicalize result 并计算 digest；
4. 在短事务内以相同 claim token 完成 snapshot；
5. 返回刚写入或由竞争者已经写入的 snapshot。

不得在持有 SQLite write lock 时执行 SSH、SFTP 或 Slurm 命令。

### 5.3 Lease 恢复

如果捕获进程在步骤 2 或 3 崩溃，`capturing` lease 会在有限时间后过期。新客户端可以原子接管，
避免 completion 永久卡住。

- lease 时间必须可测试，不依赖后台 daemon；
- 非 owner 不得覆盖仍有效的 claim；
- takeover 后旧 owner 的迟到写入必须因 token 不匹配而失败；
- 并发读取允许暂时重复进行 Backend I/O，但最终只能提交一个 snapshot。

### 5.4 Canonicalization

digest 输入必须固定：

- UTF-8；
- JSON object key 排序；
- 紧凑 separators；
- 明确 schema version；
- 不包含每次读取都会变化的字段；
- `captured_at` 放在 snapshot metadata，不进入 result digest。

相同 result 在 Python 3.10–3.14 上必须产生同一 digest。

### 5.5 边界与预算

- snapshot result 继续服从 `max_return_bytes` 和 `log_tail_lines`；
- 存储前验证序列化后大小，不允许无界 metadata 绕过预算；
- Artifact 数量和单项 metadata 需要独立上限；
- 任何截断必须显式记录，不能静默丢字段；
- snapshot JSON 损坏或 digest 不匹配时返回明确的持久化错误，不回退到 live Backend 并伪装成
  同一个历史结果。

## 6. Backend 行为

### 6.1 Local

- runner 仍原子提交 terminal state；
- 首次 `wait` 或 completion read 捕获有界结果；
- 捕获成功后删除或修改原日志 / Artifact 不影响重放；
- queued cancellation 也创建合法的空日志 snapshot。

### 6.2 SSH

- terminal event 已存在但 snapshot 不存在时，允许通过 SSH 重试捕获；
- 捕获成功后所有 replay 不再启动 SSH / SFTP；
- 捕获前断线继续使用 v0.5 的 `unreachable_job_ids` 与 cursor 规则；
- 不在远端安装新 daemon。

### 6.3 Slurm

- `squeue` / `sacct` 仍负责发现终态；
- 首次捕获通过现有 SFTP 数据通道读取有界日志和声明 Artifact；
- 捕获后即使 Job accounting 记录或计算节点文件被清理，Agent-facing result 仍可重放；
- Slurm 继续是唯一物理资源 Scheduler。

## 7. v0.5 升级策略

升级必须原地、惰性完成：

- 新建 snapshot 表，不重写现有 Job、queue、task 或 completion ID；
- v0.5 历史 completion 初始都处于 snapshot pending；
- 第一次读取时捕获，不在升级事务中批量访问文件或远端主机；
- 已丢失的 Local 文件按当时可观察到的 bounded result 捕获，并明确标记 Artifact missing；
- SSH / Slurm 不可达时保持 pending，不生成伪结果；
- 重复打开数据库不复制 snapshot。

## 8. P0 交付范围

- 不可变、唯一的 terminal result snapshot；
- capture lease、崩溃恢复与并发提交保护；
- canonical JSON 与 SHA-256 digest；
- `wait`、completion feed、MCP Tasks 共用 snapshot；
- Local、SSH、Slurm 的首次捕获与离线 replay；
- v0.5 数据库惰性升级；
- snapshot 状态 inspect；
- JSON Schema、Reference、Agent Skill 与 Changelog 更新；
- installed-wheel 离线重放 smoke test；
- snapshot 大小和 replay Backend 调用次数的机器可读 benchmark。

## 9. 明确非目标

v0.7 不加入：

- 大文件 Artifact 上传、下载或内容寻址对象存储；
- 完整日志归档或日志流式传输；
- 自动 retention、GC 或磁盘配额；
- workset、workflow key、named consumer 或 server-side ack；
- Webhook、桌面通知或 Agent 主动唤醒；
- DAG、Job dependency 或成功后自动执行下一条命令；
- priority、抢占、GPU discovery 或动态资源配额；
- daemon、HTTP control plane 或托管服务；
- 新 Backend。

## 10. 实施里程碑

### Milestone 0：冻结 Result Schema

产出：

- snapshot metadata 与 canonical result Schema；
- digest 计算规则与跨 Python golden vectors；
- live `logs` 与 immutable result 的语义边界；
- 大小预算和 Artifact metadata 上限。

退出条件：不同实现可以根据同一 fixture 生成字节级一致的 digest。

### Milestone 1：Store 与 Capture Lease

主要文件：

- `src/awaitless/db.py`：snapshot 表、claim、finalize、takeover 和读取；
- `src/awaitless/service.py`：统一 materialize / load result；
- `tests/test_db.py`：并发 claim、过期接管、迟到 owner 和迁移。

退出条件：两个独立 SQLite connection 并发捕获时只留下一个 immutable snapshot。

### Milestone 2：Local 与现有接口

主要工作：

- `wait` 与 `completions` 共用 snapshot；
- Local 成功、失败、timeout、lost 和 queued cancellation；
- `inspect` 显示 pending / capturing / captured；
- 更新 completion JSON Schema。

退出条件：首次读取后修改原日志与 JSON Artifact，所有后续结果和 digest 仍保持不变。

### Milestone 3：SSH / Slurm 离线重放

主要工作：

- 捕获前不可达保持 cursor；
- 捕获后禁用 SSH / SFTP 仍可 `wait` 和 replay；
- Slurm 状态映射和 Artifact 结果复用 snapshot；
- capture lease 崩溃恢复。

退出条件：一次远端成功捕获后，新的完全离线客户端能取回同一结果且不产生 Backend 调用。

### Milestone 4：证据与发布

产出：

- 安装 wheel 后执行 capture → disconnect → backend unavailable → replay；
- 可复现 benchmark 比较首次捕获后多次 replay 的 Backend 调用；
- README、Reference、MCP 文档、Agent Skill 与 Changelog；
- v0.7.0 版本与发布元数据。

退出条件：每个 snapshot 声明都有自动化测试或机器可读证据，sdist / wheel smoke 通过。

## 11. 验收标准

| 场景 | 必须观察到的结果 |
|---|---|
| Local 不可变重放 | 首次捕获后修改或删除日志 / JSON Artifact，结果与 digest 不变 |
| SSH 离线重放 | 捕获后禁用 SSH，`wait` 与 completion replay 仍成功且无 SSH 调用 |
| Slurm 离线重放 | 捕获后 scheduler / SFTP 不可用，已有 snapshot 仍可读取 |
| 捕获前断线 | 不创建空 snapshot、不前进 cursor，返回 unreachable Job |
| 并发首次读取 | 多客户端得到相同 digest，数据库只有一份 captured snapshot |
| Capturer 崩溃 | lease 到期后新客户端接管，旧 owner 不能覆盖新结果 |
| Cursor 重放 | 相同 completion ID 永远返回相同 snapshot digest 与 result |
| wait / feed 一致 | 两条接口无论调用顺序都返回同一 snapshot |
| MCP Tasks 一致 | terminal Task result 与普通 MCP Tool 使用同一 snapshot |
| 大日志 | snapshot 服从预算并保留 `truncated` 标记 |
| 大 Artifact | 只冻结 metadata，不把大文件内容写入 SQLite |
| 数据损坏 | digest 不匹配时明确失败，不静默回退到 live result |
| v0.5 升级 | Job、queue、Task ID 和 completion ID 不变，snapshot 惰性生成 |
| Wheel smoke | 从安装后的 wheel 完成捕获、断线和离线重放 |

## 12. 质量与发布门槛

### 正确性

- 每个 terminal completion 最多一个 captured snapshot；
- snapshot 一旦 captured 不可通过普通代码路径更新；
- result digest 跨支持的 Python 版本稳定；
- 任何捕获失败都不能消费 cursor；
- terminal state、snapshot 与接口结果不存在互相矛盾的状态。

### 兼容性

- v0.5 的 CLI、MCP Tasks、completion cursor、queue 和幂等提交测试全部保持通过；
- additive Schema 变更不破坏忽略未知字段的 v0.5 客户端；
- Python 3.10–3.14 CI 全部通过；
- v0.5 SQLite fixture 原地升级测试通过。

### 性能与上下文

- snapshot 命中不得访问 Backend；
- SQLite write transaction 中不得发生网络 I/O；
- snapshot 字节数受明确预算约束；
- benchmark 只报告可验证的 Backend / Agent-visible 调用与字节数，不推断模型 token 收益。

## 13. 风险与缓解

### 13.1 Snapshot 增加本地磁盘占用

缓解：只保存 bounded result，记录精确 `size_bytes`；v0.7 收集真实分布后再设计 retention。

### 13.2 第一次捕获发生得太晚

无 daemon 设计意味着无人调用时不会主动连接远端。缓解：Local runner 可评估在终态后直接捕获；
SSH / Slurm 仍明确承诺“first successful observation 后持久”，不虚构离线主动同步。

### 13.3 用户误以为大型 Artifact 已被备份

缓解：每个 Artifact 明确标记内容是否 embedded / snapshotted；文档避免使用“完整 Artifact
归档”等表述。

### 13.4 Live logs 与 snapshot logs 不同

缓解：`wait` / completion 是历史不可变结果，`logs` 是显式 live observation；CLI 与文档使用
不同字段说明来源和时间。

### 13.5 Capture lease 引入复杂状态

缓解：只允许 capturing / captured 两态，失败通过 lease 过期重试，不持久化不可恢复的 failed
状态；所有 owner 写入使用 token compare-and-swap。

## 14. 发布后决策

v0.7 发布后记录：

- 每个 snapshot 的大小分布；
- 首次捕获失败与恢复比例；
- snapshot replay 避免的 SSH / SFTP / Slurm 调用；
- 同一 completion 的实际重放次数；
- Agent 丢失 Job ID 集合或 cursor 的真实案例。

只有证据表明客户端状态管理成为下一主要障碍时，v0.8 才进入 durable workset、workflow key
和 named consumer checkpoint。即使未来加入这些对象，也继续坚持：

> **Awaitless persists execution facts; the Agent owns the next decision.**
