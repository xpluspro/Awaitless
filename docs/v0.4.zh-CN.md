# Awaitless v0.4：提交任务，也提交等待资源的意图

## 一句话定位

Agent 只提交一次工作意图；Awaitless 同时负责等待任务可以开始，以及等待任务完成。

## 发布范围

v0.4 只加入一个清晰的调度 MVP：持久化命名 queue、FIFO admission、固定并发上限、
非抢占执行和 queued job cancellation。它不加入 priority、抢占、queue reorder、DAG
或 GPU discovery。

```text
awaitless queue create gpu0 --concurrency 1
awaitless submit --queue gpu0 -- python train_a.py
awaitless submit --queue gpu0 -- python train_b.py
```

queue 只用于 Local 和 SSH backend：

- Local queue 通过共享 Awaitless SQLite 数据库协调并发；
- SSH queue 通过目标主机上的 durable pending 文件和 `flock` slot 协调多个独立客户端，
  因此目标主机必须提供 `flock`；
- Slurm job 继续完全由 Slurm 调度，Awaitless 不在 Slurm 外再叠加一层 queue，
  `--backend slurm --queue ...` 会被拒绝。

## 状态与恢复语义

- 用户可见的 `pending` 状态更名为 `queued`；Slurm `PENDING` 也映射为 `queued`。
- runtime timeout 从 command 真正开始执行时计时，不包含等待 queue slot 的时间。
- 取消 queued job 会阻止其 command 启动。
- Awaitless 不安装常驻或开机启动 daemon；主机重启后需要一次 Awaitless CLI/MCP
  调用触发恢复与协调。

## 真实机器验收

2026-08-11 在 queue 实现提交 `cb8a31f068358226b5ba8f5cf6b668f830ecc546`
上完成发布前验收。测试只运行 Python 文件写入与 `sleep`，没有运行 GPU/NPU 或其他
高负载任务。

| 验收项 | 结果 | 实际观察 |
|---|---|---|
| Local concurrency 1 | 通过 | A 完成后 B 才开始，事件严格 FIFO |
| Local concurrency 2 | 通过 | 4 个 job 的实际同时运行峰值为 2 |
| queued cancellation | 通过 | Local 与 SSH 中被取消的 queued command 均未执行 |
| `0.3.0` 数据库原地升级 | 通过 | PyPI `0.3.0` 历史 job 保留，新 queue schema 与 job 正常工作 |
| 两个独立 SSH 客户端共享 queue | 通过 | 不同本地数据目录提交到同一远端 queue，第二个 job 为 `queued`，执行严格 FIFO |
| SSH 残留检查 | 通过 | pending 文件 0、持有中的 slot lock 0、存活 wrapper 0 |
| SSH `/tmp` 清理 | 通过 | 专用远端目录已删除，复核残留目录数为 0 |
| 真实 Slurm `PENDING → queued` | 条件跳过 | 验收目标没有安装 `sbatch`、`squeue`、`sacct` 或 `scancel` |

SSH 验收使用 `xflops_zhiyuan` 的独立 `/tmp/awaitless-acceptance-0.4.0.*`
目录。验收结束前先确认没有存活 wrapper 或持有中的 slot lock，再删除该目录；清理过程
没有终止任何进程。机器可读记录位于
[`assets/queue-acceptance-0.4.0.json`](../assets/queue-acceptance-0.4.0.json)。
